# Secrets and cryptographic key lifecycle

The deployment operator owns runtime keys and records their purpose, environment, custodian, creation date, retirement date and incident history in the deployment's secret manager. Keep the record separate from the secret values. Review active keys quarterly and after changes to the deployment or its integrations. The lifecycle follows the generation, activation, deactivation, archival and destruction phases in [NIST SP 800-57 Part 1](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final).

## Generate, distribute and activate

- Generate independent keys for each deployment and purpose using the application's key generator, an approved secret manager or the credential issuer. Store secrets in the operator's secret manager or in a protected local configuration file available only to the service account. Protect any generated `storage/app.key` file and its volume backups with equivalent access controls.
- Give each shared secret to the two participating systems only, such as Excubia and one webhook receiver. Keep each private key with its owning service, client or authenticator. Give operators administrative access by role, audit access to secrets, and distribute only public keys and certificates for verification. Use separate credentials if another consumer needs access.
- Set the intended expiry or rotation date before use. Deploy new credentials to an isolated test instance before activating them in production. Keep key values out of Git, logs, CI output, screenshots and incident records.

## Runtime credentials

The operator rotates deployment credentials through the issuing system, updates the deployment secret manager, restarts affected processes, and verifies the relevant connection before revoking the old value. Set each third-party credential's period using its issuer's limit and the deployment's risk assessment. Reissue immediately on suspected exposure and retire credentials as soon as their integration is removed.

## Rotate the application key

1. Confirm access to a database backup and its corresponding key as described under [Backups](../self-hosting.md#backups). Rehearse the rotation against an isolated restore with test integrations. If `PASSKEYS_USER_HANDLE_SECRET` falls back to the old app key, set a separately managed stable handle secret to the same current value before routine app-key rotation to preserve the namespace.
2. Generate a fresh 32-byte key with Laravel's `php artisan key:generate --show` in a restricted operator terminal. Store the output directly in the secret manager. Set the new `APP_KEY` and put the old key in `APP_PREVIOUS_KEYS` for the transition. Apply these values to the web service and all workers together, rebuild cached configuration where used, and restart long-running processes. [Laravel key rotation](https://laravel.com/docs/13.x/encryption#gracefully-rotating-encryption-keys).
3. Verify existing encrypted settings, TOTP, passkey registration and sign-in, SSO, and signed webhook delivery where enabled. Re-encrypt retained data or reissue each credential under the new key before retiring the previous key. Laravel's fallback permits reads of old ciphertext. An ordinary read leaves that ciphertext under the original key.
4. Remove the previous key from the active configuration after verifying that retained ciphertext can be read with the new key alone. Verify again after removing the fallback in the isolated restore. Restrict archived decryption keys to backup recovery and retain them only as long as an authorized backup needs them. Delete service and backup copies when their retention ends, and record retirement or destruction without recording the value.

`tests/Unit/Console/InstallCommandTest.php` verifies generation on install and preservation on reinstall. `tests/Feature/Settings/AlertsTest.php` verifies issue and rotation of the alert webhook secret, including the grace period.

## After a leak

1. Isolate the affected service if needed, revoke or rotate the affected secret, and stop accepting anything signed by a compromised key. A compromised `APP_KEY` must be removed from live configuration, including `APP_PREVIOUS_KEYS`. When recovery requires the old key, use it only in isolated recovery to decrypt retained data, then re-encrypt or replace the values with new keys.
2. Invalidate affected sessions, signed URLs, tokens or other issued credentials and replace affected TOTP, SSO or integration secrets where the leak exposed their ciphertext and key. Confirm the replacement works using the relevant deployment probe above.
3. Review audit logs for unexpected access or use of the old credential. Record the exposure window, affected services, containment, verification and retirement in the incident record without copying any secret values.
