# Cryptographic inventory

This inventory covers Excubia's runtime cryptography, including the Laravel and qiick packages that implement it. The maintainer reviews the inventory on changes to authentication, storage, integrations, dependencies or deployment topology and at least quarterly. The deployment operator keeps the associated key and certificate records and reviews them at renewal. Follow the [secrets runbook](runbooks/secrets.md) for activation, rotation, recovery and retirement.

## Deployment certificates

| TLS boundary                                                                | Certificate and owner                                                                                                                        | Allowed use                                                                                                                                                                                                                                 |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public HTTPS, including dashboard, REST, ingest and MCP                     | The operator or hosting platform provisions the web certificate and keeps its private key at the TLS terminator.                             | Authenticate the named Excubia host and protect client traffic in transit. Keep the web key scoped to the operator-approved hostnames. [Self-hosting](self-hosting.md).                                                                     |
| Configured internal HTTPS or encrypted database, Redis and SMTP connections | The operator provisions the service certificate and trusted roots where these transports use TLS. The service owner retains its private key. | Authenticate the named internal service. If a deployment uses a client certificate, record its separate purpose and owner. Review connection settings in `config/database.php`, `config/mail.php` and the deployment environment.           |
| Outbound HTTPS to providers and webhooks                                    | Service owners hold their own private keys. Excubia validates remote certificates and names against the platform or operator's trust store.  | Authenticate the exact configured remote host, including the OIDC issuer, HIBP, notification and AI providers, the S3 endpoint and the intended webhook receiver. Use the public CA certificates in the trust store for chain verification. |

For each deployed certificate record its owner, endpoint, subject or SANs, issuer, serial number or SHA-256 fingerprint, signature algorithm, key type and size, expiration date and next renewal check. Store a reference to the private key's protected location when the operator owns it. For an external service or managed certificate, record the provider and verification method.

## Verify changes

1. Compare authentication, encryption, hashing, signing and transport configuration changes with the inventory. Follow affected dependencies in `composer.lock` to their verification or signing code. Add any new key, algorithm, certificate or allowed use before deployment.
2. In an authorized test deployment, check the certificate chain, hostname, algorithm, expiration and key type for the HTTPS edge and every configured internal TLS endpoint against the deployment inventory. Use the endpoint's trust store and keep only public certificate metadata as evidence.
3. Run the relevant product checks. `tests/Feature/Auth/TwoFactorChallengeTest.php` covers TOTP challenges, `tests/Feature/Settings/AlertsTest.php` covers webhook signing and rotation, and `tests/Feature/Settings/ApiKeysTest.php` covers key matching and rotation.

For a direct TLS endpoint, set `tls_host`, `tls_port` and `tls_ca_bundle` to the expected hostname, port and trusted CA bundle. Verify the connection and inspect the leaf certificate's metadata. Use the appropriate protocol negotiation for services that upgrade their connection to TLS.

```sh
certificate_capture=$(mktemp)
openssl s_client -connect "$tls_host:$tls_port" -servername "$tls_host" \
    -verify_hostname "$tls_host" -verify_return_error -CAfile "$tls_ca_bundle" \
    -showcerts </dev/null > "$certificate_capture" &&
openssl x509 -in "$certificate_capture" -noout -subject -issuer -serial \
    -dates -sha256 -fingerprint -text
rm -f "$certificate_capture"
```
