# Changelog

All notable changes to **Excubia App** (`qiick-io/excubia-app`) are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
Each version ends with **Upgrade notes**: breaking changes, new settings and the steps to
upgrade from the version before (see [docs/self-hosting.md](docs/self-hosting.md#upgrades)).

## [Unreleased]

### Added

- **Assignee on exception groups and findings** (#254): who is on it. The Exceptions and Findings drawers have an **Assignee** select listing the active users who can see the project (visibility and the #253 scope), saved at once; assigning takes the same permission as handling the item (`can-manage-exceptions`, `can-dismiss-findings`) and the server refuses an assignee who cannot see the project. Both lists show the assignee and gain an **Assigned to me** filter; the dashboard shows **Assigned to you** (open exception groups and open, undismissed findings per project) with links that open the tab already filtered (`?assigned=me`). Assignments are logged in the activity log (`assigned` / `unassigned`), and a finding's history records who assigned it to whom. A `finding.new` or `finding.resolved` alert of an assigned finding names the assignee in its text and data (`assignee`). Not an issue tracker: no due dates, comments or workflow. New nullable `assigned_user_id` columns on `exception_groups`, `findings` and `finding_events` (indexed; a deleted user leaves the item unassigned).
- **Project access by scope** (#253): permissions say what, scope says where. A user group can now be linked to project groups (**Project scope** in the group drawer, admins only); its members also see the projects of those groups, admin-only ones included, while their global roles still decide what they can do there. `Project::visibleTo()` stays the single access filter (one subquery, no extra query per check) and `ProjectPolicy::view` uses it, so lists, the project picker, the fleet, the dashboard, project pages, alert email recipients and the AI tools all follow the scope. Non-admins cannot change a group's scope, nor join or leave a group that carries one. New table `user_group_project_group` with its own `id`, so a per-scope role can be added later in an additive migration.
- **Application section on the overview** (#250): after infrastructure and dependencies, three cards over the page's range (`?range=` / `?from=&to=` now apply to the overview too; its attention list still lists every exception group): **Exceptions** (occurrences per bucket and the five groups seen most), **Routes** (the slowest by p95 and the most failing by 5xx) and **Jobs** (processed against failed per bucket; the runtime payload gains `jobTimeline`). Each card has a View ↗ link to its tab with the range; a card without data names the excubia.json key that turns its type on. Released job attempts are not in excubia-core's payload, so they are not shown.
- **From a chart to its rows** (#249): a click on a bucket of a range chart narrows the page to that bucket (custom range, #247) and scrolls to the table behind it: routes for the requests and duration charts, the log levels for the error logs, models for the AI spend, tasks for the schedule runs (an exception's occurrences stay in its drawer). Those chart cards get a **View ↗** link to the same table that keeps the URL and its range, the keyboard path next to the click.
- **Drag to zoom** (#248): dragging across a time chart of the Runtime, AI, Exceptions or Schedule tab (requests, duration, error logs, AI spend, an exception's occurrences, schedule runs) highlights the buckets and, on release, makes them the page's custom range (`?from=&to=`, #247). Escape or leaving the chart cancels; a single bucket is ignored. Mouse only: the time range picker stays the keyboard and screen reader way to set the same range.
- **Custom time range** (#247): next to the presets (1h–14d), the Runtime, AI, Exceptions and Schedule tabs take a custom range from a date and time to a date and time, picked on the registry date range picker with times (`@qiick/date-range-picker`, app-ui #62; adds `react-day-picker` through `@qiick/calendar`) and kept in the URL as `?from=&to=` (UTC), so a view can be shared; Clear goes back to the default preset. The server validates it (from before to, at most 14 days, inside the runtime retention, the end clamped to now) and falls back to the preset otherwise. The bucket follows the length like the presets (per minute up to 2 hours … per day beyond 8 days), at least hourly once the span reaches past the per-minute window. Every query of those tabs now ends at the range's end instead of now.
- **Requests by status and duration charts** (#251, #246): on the Runtime tab, "Requests over time" stacks each bucket as 1/2/3xx, 4xx and 5xx from the requests' `statusClass` (4xx were counted as successful before), with the three counts on the Requests card and the bucket total in the tooltip. A **Duration** chart beside it draws the average and p95 per bucket (p95 from the bucket's summed latency histograms, capped at its slowest request) with the range's average, p95 and slowest in its header; a bucket without requests is a gap, not a zero. Both keep the deploy markers. The runtime payload's request `timeline` points are now `{at, ok, clientErrors, serverErrors, averageMs, p95Ms}`.
- **Project groups** (#252): generic groups of projects (a client, a team, a product line, an environment) under **Project groups** (`can-{show,create,edit,delete}-project-groups`, granted to admins). A project may sit in several groups; a group's drawer picks projects from those the user can see, and a non-admin editing a group never drops the admin-only projects in it. The dashboard narrows to one group (`?group=id`), offering only groups holding a project the user can see, and alert channels (Settings → Integrations) and alert emails can pick project groups next to projects: a project added to a picked group later is included. Groups grant no access by themselves; project access by group follows in #253. The picker's own strings (`picker.*`) are now translated.
- **Capabilities in push answers** (#239, excubia-core design 1.1 §10 A2): the `201` and `200` bodies of `POST /api/runtime` and `/api/exceptions` add `capabilities` with `privacyLevel` (always `aggregate`), `types` (the runtime types this app stores) and `skipped` (entries of the batch it skips; `0` on exceptions). `status` and every error body are unchanged, and `/api/reports` answers as before. excubia-core 1.0 ignores the key; core 1.1 reads it to stop sending types the app drops and to negotiate personal data levels. Clients must ignore unknown keys in success bodies (`docs/API.md`); the contract snapshot `tests/Fixtures/ingest-api-contract.json` is updated.
- **Runtime downsampling** (#212): runtime minutes are kept per minute for 48 hours (`EXCUBIA_RUNTIME_MINUTE_HOURS`, at least 24), then `excubia:downsample-runtime` (hourly) folds them into one row per series and hour with the same dimensions and merged metrics, so cards, tables, percentiles and charts over 24 h, 7 d and 14 d read the same before and after the fold. A busy project (55 series) now holds about 75 MB on SQLite, 88 MB on PostgreSQL and 108 MB on MySQL over the default 14 days, down from 470 to 600 MB. Pushed batch ids are kept 14 days instead of the longer retention (90 days). `scripts/load/ingest-load.php --fold` measures the sizes.
- **Exception occurrence retention** (#214): the per-minute exception occurrences follow the runtime minutes: `excubia:downsample-runtime` (hourly) also folds the occurrences older than `EXCUBIA_RUNTIME_MINUTE_HOURS` into one row per group and hour, and `excubia:prune-telemetry` deletes them after 14 days (`EXCUBIA_EXCEPTION_OCCURRENCE_DAYS`, at least 14, the longest range; never longer than the exceptions retention). Exception groups still stay for the exceptions retention (90 days) with their totals, first and last seen and releases, and the Exceptions tab ("In range" counts and each group's chart) and the weekly digest show the same numbers before and after the fold. A busy project's occurrences take about 1 MB on SQLite, 1.4 MB on PostgreSQL and 2.2 MB on MySQL instead of 22, 29 and 70 MB over 90 days. `scripts/load/ingest-load.php --fold` measures them too.
- **Health probes and image publishing, as externa-core:** auth-free `GET /health/live` (`{"status":"ok"}`) and `GET /health/ready` (database, and Redis when a driver uses it; 503 when a check fails), used by the image `HEALTHCHECK` and the Docker CI smoke test (`/up` stays). A release tag `vX.Y.Z` now publishes `ghcr.io/qiick-io/excubia-app` (amd64 and arm64) with the exact version, `MAJOR.MINOR` for stable releases and `latest` for the newest stable one; a manual run re-publishes a tag.
- **Install and upgrade like externa-core:** `composer create-project qiick/excubia-app` only copies `.env` and runs `key:generate`, then points to `php artisan excubia:install`. That command writes `.env` (app name and URL, SQLite / PostgreSQL / MySQL / MariaDB), migrates, seeds the permissions and the system project, links storage and builds the frontend; it is interactive, or answers from options with `--no-interaction` for CI, and the first admin is still created at `/setup`. `php artisan excubia:upgrade` runs migrate, the permission and system project sync, `optimize:clear` and `queue:restart`, refuses production or a dirty tree without `--force`, and can merge an official tag with `--sync-upstream=vX.Y.Z` (`--dry-run` lists the files first). create-project is the install path, not the update channel (README).
- **AI usage and cost** (#129, excubia-core 1.0.0-beta.4 `ai` and `aiTool`, off by default in the core): the runtime ingest stores Laravel AI SDK operations (operation, provider, model, agent; calls, failed attempts, failovers, durations, histograms and the nullable token, audio and search-unit usage with null-safe sums) and agent tool calls, rolls them up hourly, and sums them per project, day, provider and model (`ai_usage_days`, kept at least 62 days). A project **AI** tab (time range picker) shows estimated spend per bucket, calls, error rate, failovers, p95 latency, the token split (uncached input, cache reads and writes, output, reasoning), the breakdown by model, provider and agent, tool calls and failures, and the month to date against an optional monthly budget. **Settings → AI prices** (`can-manage-alerts`) holds the editable price table per provider and model (input, cache read, cache write, output, reasoning, image tokens per 1M; audio per second; search units), seeded with estimates dated 2026-11-08 to verify; models without a price show tokens without cost. New alerts, all off by default: `ai.budget_warning` / `ai.budget_exceeded` at 80 % / 100 % of the monthly budget (set on the AI tab), `ai.spend_spike` against the 7-day average and `ai.error_rate` (Settings → Integrations). The weekly digest shows the AI spend of the week against the week before. Prompts, responses and tool arguments are never received, and the tab says so.
- **AI price history** (#202): a row of Settings → AI prices may start on a day (`effective_from`, UTC; empty means since always, as every row saved before), and each day of usage is priced with the row in force that day, so a price change no longer reprices past days. "New price from a date" adds a dated copy of a row below it. The defaults carry the Gemini 3.8 Flash change of 2027-01-01 (input $1.50, cache read $0.15, output $7.50 per 1M); Gemini 2.5 Pro, billed as 3.8 Flash from 2026-12-01, follows it. The AI tab totals and breakdowns now split their sums at price-change days instead of pricing a whole range at its last minute. A table saved before keeps its rows: add the dated Gemini 3.8 Flash row (or restore the defaults) to get the 2027 price.
- **Reverb servers** (#175, excubia-core `reverb` and `laravel-reverb`, core #215, off by default in the core): the runtime ingest stores Laravel Reverb aggregates per server and Reverb app id (counters add up, the `maxConnections` gauge keeps the larger value; any app id is stored, never rejected). A **Reverb** card on the Runtime tab shows messages received and sent, connections opened, rejected and pruned, errors, channels created and removed by type (public, private, presence) and the peak of connections, with the reachability and connect time of the Reverb server from the latest report's `laravel-reverb` check, which has its label and explanation under Infrastructure.
- **Octane workers** (#168, excubia-core `octane` and `laravel-octane-config`, core #213, off by default in the core): the runtime ingest stores Laravel Octane worker aggregates per server, Octane server and worker type (counters add up, `maxRequestsAtStop`, `maxMb` and `maxGrowthMb` keep the larger value; unknown `octaneServer` and `workerType` values are stored, never rejected). An **Octane workers** card on the Runtime tab shows requests, tasks and ticks, worker starts and stops, worker errors, the most memory after a request and its largest growth since a worker's first request (a "possible leak" badge from 32 MB), and the requests at stop (average and most) next to `octane.max_requests` from the `laravel-octane-config` check, which has its label and explanation under Configuration.
- **Billing webhooks** (#178, excubia-core `billingWebhook` and `laravel-cashier`, core #217, off by default in the core): the runtime ingest stores Laravel Cashier (Stripe and Paddle) webhook aggregates per provider and event type (received, handled, failed, durations and histograms, and the failed-payment, payment-action-required and subscription-canceled signals, all summed; unknown `provider` and `eventType` values are stored, never rejected). A **Billing webhooks** card on the Runtime tab shows, per provider and event type, webhooks received, handled and failed with the failure rate, p95 and slowest handling time and the three payment signals, with their totals over the range as badges; without data it names `runtime.billing.enabled`. The `laravel-cashier` check (webhook secret, test keys in production, webhook route) has its label and explanation under Configuration. Two new alerts in Settings → Integrations, off by default: `billing.webhook_failures` (a provider's webhooks failed at least the threshold of times in the last hour) and `billing.payment_failed` (a provider reported failed payments in the last hour).
- **Authentication and API tokens** (#180, excubia-core `auth` and `laravel-api-tokens`, core #219, off by default in the core): the runtime ingest stores Laravel authentication aggregates per guard (successful logins, failed logins, lockouts and Sanctum token authentications, all summed; any guard name is stored, never rejected). An **Authentication** card on the Runtime tab shows, per guard, logins, failed logins with the failure rate, lockouts and token authentications; without data it names `runtime.auth.enabled`. The `laravel-api-tokens` check (Sanctum token expiration, stale tokens and stateful domains; Passport keys, key file permissions and token lifetimes) has its label and explanation under Configuration. A new alert in Settings → Integrations, off by default: `auth.failed_login_spike` (a guard recorded at least the threshold of failed logins in the last hour).
- **Search (Scout)** (#184, excubia-core `scout`, core #222, off by default in the core): the runtime ingest stores Laravel Scout aggregates per model class, engine and operation (jobs, failures, records synced, durations and histograms of the queued `index` and `remove` jobs; searches started, without durations; any `engine` or `operation` value is stored, never rejected). A **Search (Scout)** card on the Runtime tab shows, per model, engine and operation, the count, failed index jobs with the failure rate, records synced, p95 and slowest job time; without data it names `runtime.scout.enabled`, and its description notes that index updates with `scout.queue` off are not recorded. A new alert in Settings → Integrations, off by default: `scout.index_failures` (a model's Scout index jobs failed at least the threshold of times in the last hour).
- **Feature flags (Pennant)** (#189, excubia-core `pennant`, core #226, off by default in the core): the runtime ingest stores Laravel Pennant aggregates per feature (checks that found the feature active or inactive, first resolutions for a scope and checks of an undefined feature, all summed; any feature name, hashed ones included, is stored, never rejected). A **Feature flags (Pennant)** card on the Runtime tab shows, per feature, the checks with the active / inactive split and the active share, first resolutions and undefined-feature checks (highlighted above 0, and listed as badges); names core hashed carry a "hashed" badge; without data it names `runtime.pennant.enabled`. **Stale flags** are derived from the stored minutes, without a core check: a feature checked on each of the last N days (Settings → General → Checks, `pennant_stale_after_days`, default 30, `EXCUBIA_PENNANT_STALE_AFTER_DAYS`) with always the same value is listed as "always on" or "always off"; when the runtime retention is shorter than N the card judges over the retention and says so. By default it records every type the installed excubia-core collects and the app stores (`cache` sampled at 10 %); `EXCUBIA_SELF_MONITORING_TYPES` (comma-separated `excubia.json` keys, or `all`) chooses them in `.env`, so upgrades keep the choice. ### Security

- Security review before the beta (#51): `docs/SECURITY-MODEL.md` (every data flow: what is received, stored, kept and who sees it) and the supported 1.x versions in `SECURITY.md`. Fixed: the push rate limit is keyed by project or IP instead of the presented token; alert deliveries refuse IPv6 and IPv4-mapped private addresses and hosts that do not resolve, connect to the checked address, and never quote the URL in errors; the Slack incoming-webhook URL is stored encrypted and write-only; evidence links must be `http(s)`; the weekly digest escapes Markdown from pushed strings; the session cookie is `Secure` by default when `APP_URL` is https. A test walks every named route as a reader and as a non-admin user with every permission.
- Install-wide pages respect project visibility (#152): Settings → System lists pushes, skipped runtime types and failed alert deliveries only for the projects the viewer may see, and the Activity log hides entries about admin-only (and, for non-admins, deleted) projects, so a non-admin holding `can-show-system` or `can-show-activity-logs` no longer sees admin-only project names. The Jobs page shows no project names.
- Baseline security headers on every web response (#153): `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and a minimal `Permissions-Policy`; `Strict-Transport-Security` on https requests when `EXCUBIA_HSTS_MAX_AGE` is set (off by default).
- Role escalation (#151): you can only grant what you hold. Assigning roles to a user or a group, and putting permissions into a custom role, accept only roles and permissions the acting user holds (a role counts as held when its permissions are all held; `admin` needs the `admin` role, `super-admin` a super-admin). Users, groups and custom roles that carry something the actor could not grant are read-only for them, so nobody strips, resets or takes over a stronger account. Only a super-admin may change their own roles, join or leave a group that carries roles, or change the roles of a group they belong to. The user and group drawers offer only grantable roles and lock the role picker on your own account and groups.
- OIDC sign-in uses PKCE (`S256`) on the authorization request and the token exchange, and the redirect and callback routes are throttled to 10 requests per minute (#154).
- No known-credential admin from `db:seed` (#225): the development super-admin (`INITIAL_SUPER_ADMIN_*`) is seeded only where `APP_ENV` is `local` or `testing` and `INITIAL_SUPER_ADMIN_PASSWORD` is set; `.env.example` no longer ships the password `password`, so `migrate --seed --force` on a server creates no user and `/setup` stays the way to the first admin. **Settings → System** flags a `superadmin@example.com` account outside local and testing (an error while its password is still `password`).

### Upgrade notes

- **First release:** there is nothing to upgrade from. Install with `composer create-project qiick/excubia-app` and `php artisan excubia:install`, or the Docker image (`ghcr.io/qiick-io/excubia-app`); see [docs/self-hosting.md](docs/self-hosting.md).
- **Migrations are frozen and forward-only from this release on** (#193): released migrations are never edited again, every schema change is a new migration, and each release upgrades the previous database with `php artisan migrate --force` (run by `excubia:upgrade` and the Docker entrypoint). Back up the database before every upgrade. Development databases created before this release need one last fresh migration.
- **Upgrade steps from here on (source):** check out or merge the new tag, then `composer install --no-dev -o`, `npm ci && npm run build`, `php artisan excubia:upgrade --force` and `php artisan optimize`. **Docker:** pull `ghcr.io/qiick-io/excubia-app:<version>` and recreate the containers; the `app` container migrates on start.
